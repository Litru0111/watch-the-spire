## 快速开始

```powershell
# 0) 环境自检（会告诉你每个数据源是否就绪）
.\sts2mon.cmd doctor

# 1) 导入历史对局（97 场约几秒）
.\sts2mon.cmd ingest

# 2) 打开仪表盘 http://127.0.0.1:8770
.\sts2mon.cmd serve
```

想立刻看到「实时」效果（不需要启动游戏）：

```powershell
# 把一场真实对局按时间轴重放成实时数据流
.\sts2mon.cmd demo --seed 4P41DR508X --speed 6
# 浏览器打开 http://127.0.0.1:8770/#live
```

真正打游戏时：

```powershell
# 每 0.5 秒轮询一次 mod 状态文件，变化就 diff 成事件流写库；同时提供仪表盘
.\sts2mon.cmd watch
# 游戏更新状态文件后，仪表盘「实时监控」页开始跳动
```

## 它监控什么

| 页面 | 内容 |
|---|---|
| **全局统计** | 总场次/胜率、各角色胜率与平均层数、各进阶难度胜率、死亡热点（被谁终结）、楼层压力曲线（平均 HP 与平均受伤）、遭遇战绩（回合数/均受伤/死亡率）、卡牌表现（总伤害、每次伤害）、选牌倾向（三选一拿走比例） |
| **对局记录** | 每场对局的地图与路线（有官方地图布局时画出**完整地图树 + 实际走过的路线高亮**）、逐层数据（HP/受伤/金币/获得卡牌遗物）、每场战斗的逐回合曲线与逐卡贡献、**局后总结**（多维评分 + 全局路线 + 数值变化曲线 + 卡牌抓取 + 事件选择）。**多人对局可逐玩家切换**，并给出玩家对比表 |
| **实时监控** | 当前遭遇、回合数、我方 HP 条、累计输出/承受、每回合输出、格挡吸收、出牌数、能量、最大单击、**逐回合柱状图**、**卡牌贡献表**、**实时事件流**、**卡牌抓取监控**、**事件选择监控**、**我方数值预测**（含「会不会因血量耗尽而结束」） |

## 「开局即监测」

实时监控（`watch`）**挂一个进程就够了，不用每局重启**：

* **换局自动识别**：`run_seed` 一变就说明游戏里开了新一局——程序立刻发 `run_start`
  重置状态机，把上一局**自动收尾并落库**（不会把新一局的数据灌进旧对局）。
  控制台会打印 `▶ 检测到新对局（seed=...），已切换监控目标`。
* **中途启动也能用**：对局打到一半才开监控，会立刻按当前状态建立完整基线
  （累计数值 + 逐回合曲线 + 卡牌贡献），不是从零开始空等。
* **退回主菜单**：状态文件里 `tracking=false` 且没有 encounter 时不产生事件，
  已有数据不会被篡改。
* **幂等**：同一份状态反复读取不会重复计数（曲线之和恒等于累计伤害）。

轮询节奏：**mtime 变化 + 0.5 秒间隔**（文件没变就不解析，避免重复计数与 CPU 浪费）；
同时每 3 秒或每 10 个事件强制落库一次，保证库里的实时状态不落后。

```powershell
.\sts2mon.cmd watch        # 挂着即可，打多少局都自动记录
```

覆盖这些场景的回归测试：`python tools\selftest_runboundary.py`（17 项）。

## 多人对局支持

本机 98 场存档里有 **8 场是 3 人联机局**。程序完整区分单人/多人，并为**每位玩家各做一套**统计：

* **存储**：`players` 表存每人的角色/牌组/遗物/徽章；`player_stats` 表存「某人某层」的
  HP/金币/受伤/抓牌/事件选择；`combats` 与 `turn_stats`、`card_stats` 都带 `player_id`。
* **历史对局**：`.run` 里 `players[]` 与每层 `player_stats[]` 以 Steam ID 对齐；
  本机玩家按 `local_player_id` 标记（界面上以 ★ 显示）。
* **rdps 明细**：每场战斗的 `Players[].NetId` 就是 Steam ID，直接与存档对齐——
  所以三人的逐卡伤害天然分开（实测：铁甲输出 729 / 储君 1237 / 静默猎手 1250）。
* **实时监控**：`DamageMeter` 的 `players` 是「每人一份」，程序按玩家 key 各建一条战斗与逐回合记录。
* **评分**：同一套分位校准算法分别作用到每位玩家（实测同一局：铁甲 72.5 C / 储君 85.1 A / 静默猎手 80.8 B）。
* **界面**：对局列表给多人局打「多人 N 人」标记；详情页顶部有玩家切换开关，
  并附一张玩家对比表（评分/等级/输出/承受/每回合输出/抓牌/遗物/终局 HP）。

## 局后总结与评分

评分不是拍脑袋的绝对值，而是**相对本机历史对局的分位**（100 分制）：

| 维度 | 权重 | 说明 |
|---|---|---|
| 推进深度 | 30 | 走到第几个 Act 的多少层；通关满分，死在层段 Boss 手里按 92% 上限 |
| 战斗效率 | 25 | 每回合输出（只在「有输出数据」的对局之间比较——存档不记录我方输出） |
| 生存能力 | 20 | 每层承伤的反向分位；通关直接满分 |
| 资源管理 | 15 | 金币「花掉 65% 左右」最健康 + 商店访问次数 |
| 牌组质量 | 10 | 遗物数量 + 删牌数量 |

> 分数含义：60 分 = 好于 60% 的历史对局。等级 S(≥92) / A(≥84) / B(≥74) / C(≥62) / D(≥48) / E。

总结面板还给：全局路线（每个 Act 的楼层胶囊，含 HP/受伤/获得物）、
数值变化曲线（HP / 金币 / 每层受伤，可悬停查每层数值）、卡牌抓取表（拿到/跳过/移除）、
事件与选择表。

## 开场事件（涅奥/远古）的选择

**能抓**。开场选择发生在第 1 层、且**没有任何战斗**，所以 DamageMeter 看不到——
只能从进行中存档拿。存档里第 1 层的 `player_stats` 有一个专门的字段：

```json
"ancient_choice": [
  {"TextKey": "NEW_LEAF",          "was_chosen": true},
  {"TextKey": "SCROLL_BOXES",      "was_chosen": false},
  {"TextKey": "PRECARIOUS_SHEARS", "was_chosen": false}
],
"relic_choices": [{"choice": "RELIC.NEW_LEAF", "was_picked": true}],
"cards_transformed": [{"original_card": {"id": "CARD.STRIKE_SILENT"},
                       "final_card":    {"id": "CARD.DAGGER_SPRAY"}}],
"hp_healed": 70
```

监控台会把**候选项 + 选中了哪个 + 变形/获得的牌 + 回血**都解析出来，实时显示：

```
卡牌抓取监控
  层  结果    卡牌
  1   [变化]  打击（静默猎手） → 匕首雨      远古
  1   [获得]  匕首雨 (来自 打击（静默猎手）)  远古

事件选择监控
  层  类型   房间 / 获得
  1   远古   新叶
             远古三选一：[✔新叶] [卷轴箱] [松动羊毛剪]
```

### 动作类型必须分清（一个被纠正的标注错误）

卡牌离开牌组有**两种完全不同的原因**，早期版本把它们混成了「跳过」：

| kind | 含义 | 例子 |
|---|---|---|
| `picked` | 三选一里拿走的 | 拿「匕首雨」 |
| `skipped` | 三选一里**没拿**的 | 三选一剩下两张 |
| `gained` | 从其它途径进牌组（事件/商店/宝箱/变化后的新牌） | — |
| `transformed` | 被**变化**掉的原牌（牌还在牌组，只是换了一张） | 「新叶」把「打击」变成「匕首雨」 |
| `removed` | 被**移除**的原牌（牌真的没了） | 商店删牌、事件移除 |

> 用户实测指出：遗物「新叶」的效果是**变化一张牌**，程序却把原牌标成了「跳过」。
> 原因是用 `picked: false` 一刀切成「跳过」。现在改成显式的 `kind` 字段，
> 且「变化」行会带上变化目标（`打击 → 匕首雨`），与「移除」「跳过」彻底区分。

> 说明：实时源（DamageMeter）**不含**开场选择，是新增的存档解析补上了这块；
> 历史对局（`.run`）本来就有 `event_choices`，两侧现在口径一致。

## 黑箱对局模拟器（不需要游戏）

`tools/simulate_runs.py` 用**合成数据**驱动完整链路，并以「模拟器自己编排的真值」
为独立判据断言不变量。它把每一步事实渲染成两个数据源的**真实文件格式**：

| 生成物 | 内容 |
|---|---|
| `current_run.save` | 权威 HP / 金币 / 逐层数值（含休息处、药水回血、生命上限变化） |
| `DamageMeter_combat_state.json` | 伤害、出牌、格挡、每回合曲线（含**环形缓冲淘汰**） |

然后按监控循环的真实顺序喂给 `Tracker` / `LiveState` / `Store`，核对：

* 实时 HP **必须等于**存档真值（这条能挡住「用药水回血就算错」的 bug）
* 累计输出、逐层输出、逐回合曲线必须等于真值
* 每个节点的事件**只能来自它自己那场战斗**（不混上一场）
* 每层一个节点，不因多数据源而分裂
* 事件流里的伤害合计**不能超过**真值（超过就是重复计数）
* 出牌事件必须有牌名、且必须是真实卡牌
* 重复 flush **不能**写入重复事件（落库幂等）
* 连续多局：旧局要收尾、新局从零建状态、上一局不混进新局

```powershell
python tools\simulate_runs.py --runs 200 --seed 42 --multiplayer-every 6 --ring 20
python tools\simulate_runs.py --runs 20 --sequences 3 --seq-runs 3   # 连续多局
python tools\verify_sim_kills.py   # 验证「模拟器真能抓到 bug」（注入历史 bug 看是否报错）
```

### 模拟器抓到并已修复的 bug

| bug | 后果 | 修法 |
|---|---|---|
| `LiveState.flush_events_to` 不幂等 | 每次 flush 把整场战斗的事件重写一遍，事件表条数翻几倍、界面伤害合计虚高 | 每场战斗记水位线 `Combat.persisted_events`，只写新增 |
| `diff()` 不发 `map_node` | 商店/休息处/事件/宝箱这些**非战斗层完全不记录** | 换楼层时补发 `map_node` |
| `PLAYER_STAT` 无条件建战斗 | 每个非战斗层多出一条 `encounter=UNKNOWN` 的**假战斗**，还抢走 boss 的伤害归属 | 只有真正的战斗数值才建战斗；光有 HP/金币只建节点 |
| 首读历史事件不登记去重集合 | 下一回合把同一批历史事件当新增重发，重复计数 | 首读时把事件签名登记进 `_seen_sigs` |
| 环形缓冲去重只看上一帧 | 条目被挤出后再出现会被当新增，重复计数 | 改为**跨轮询**的签名集合，按场次清空 |

> 这些 bug 都在真机上难以复现（要恰好打很多回合、恰好让缓冲淘汰），
> 但模拟器几秒钟就能稳定复现 —— 这就是它的价值。

## 我方数值预测

实时页会按当前掉血速度外推生存情况，回答「**这一局会不会因为血量耗尽而结束**」：

* **HP 用实测值**，来源是**进行中存档** `...\profile<N>\saves\current_run.save`
  （`players[0].current_hp / max_hp`）。这是唯一记录实时 HP 的数据源。
* 每层承伤 = 存档 `map_point_history[act][point].player_stats[].damage_taken` 的实测平均
* 净损 = 每层承伤 − 预估休息处回血（按生命上限 28% × 12% 楼层占比折算）
* 还能撑几层 = 当前 HP ÷ 净损；若小于本 Act 剩余层数 → 判定为「会因血量耗尽而结束」

### 曾经的错误（已修，值得记下来）

早期版本用 `估算HP = 生命上限 − 累计承伤` 代替真实 HP，界面上还标着"推算值"。
这**必然出错**：药水回血、休息处、事件治疗、生命上限变化全都不在承伤里。
实测把玩家的 **22/75 显示成 62/75**，预测方向完全反了。

现在：
* 有实测 HP 时 → 标签写「实测」，置信度 high，并注明来源
* 确实拿不到时 → HP 条画成灰色斜纹、标签写「推算值 · 不可靠」，
  文案明确写「不要据此判断能否活下来」，绝不给出误导性的数字

> DamageMeter 只统计伤害与出牌，**完全不记录我方 HP**（字段表里没有 hp）；
> rdps / `.run` 也都没有。多数据源合并时还有两个坑：
> 一是 DamageMeter 不知道楼层，两个源会各建一个地图节点，HP 挂不到战斗上；
> 二是两个源用不同的 run_id，`LiveState` 会误判「换局」而重建状态机、丢掉 HP。
> 现在楼层与 run_id 都由存档源注入，节点 id 统一按 `f{floor:03d}` 派生。

## 数据从哪来（重要）

程序把 5 个真实数据源归一化成同一套模型：

| 数据源 | 位置 | 提供什么 |
|---|---|---|
| 对局存档 `.run` | `%APPDATA%\SlayTheSpire2\steam\<id>\[modded\]profile*\saves\history\*.run` | 种子、角色、进阶、胜负、被谁终结、各 Act 的地图点序列、每层 HP/金币/受伤/选牌/遗物/药水、顶层牌组与遗物（97 场） |
| **官方地图布局** | `…\SlayTheSpire2\analytics\*.json` | `map_acts[].nodes[].coord/children`、`visited_coords`（**完整地图 + 实际路线**）。文件名时间是 **UTC**，与 `.run` 的 `start_time`（本地时间）相差 8 小时 |
| 实时战斗状态 | `…\SlayTheSpire2\DamageMeter_combat_state.json` | 由 `DamageMeter` mod 实时写盘：`turn`/`encounter`、累计输出/承受、`dpt` 每回合伤害、`dbc` 每卡伤害、`cpc` 每卡打出次数、`bbc` 每卡格挡、以及**带回合号与中文标签的事件流** |
| 战斗明细 | `…\SlayTheSpire2\rdps_meter\<种子>.json` | 每场战斗的逐卡伤害/格挡、增益与 Debuff 的给予/承受（含中文卡名） |
| 名称库（**自建**） | `.sts2mon\name_library.json`（`extract` 从 `SlayTheSpire2.pck` 提取） | **2606 个 ID → 官方中文名**（角色/卡牌/遗物/怪物/遭遇/事件/药水）。不依赖任何 mod |
| （可选补充） | `…\SlayTheSpire2\DanmakuSpire\object-catalog.json` | 装了 DanmakuSpire 时并入，**不再必需**（早期唯一的名称来源） |

因为 `.run` 文件名是写入时间戳、而 rdps 文件名是种子，程序**统一用种子作为对局 ID** 来做关联。

### 数据源的能力边界（不掩饰）

* **我方 HP / 金币**：`DamageMeter` 实测**不记录**（字段表里没有 `hp`/`max_hp`/`gold`），
  所以真机实时页的血条会显示为空、由界面明确标注，而不是编造数字。
  逐层 HP 仍然可以从 `.run` 存档与回放中拿到。
* **敌方血量**：`DamageMeter` 只统计我方，因此实时页的敌方血条标注「数据源未提供」。
* **逐卡打出次数**：rdps 明细只记录伤害来源，没有次数；这类数据的「打出」会显示为下界估算。
* **地图坐标**：只有官方 `analytics` 报告里才有（当前机器上 3 份）。其余对局退化为
  「按路线顺序的楼层时间线」，界面上会明确写出是哪一种。
* **回放的逐卡伤害是摊开的**：真实对局只有「每场战斗的逐卡伤害」总量，
  回放时按回合轮转铺开，因此回放中的单卡伤害是近似值（真机实时采集是精确的）。
* **未核对的译名**（**已解决**）：早先 `object-catalog` 只收录单体怪物，
  编队型遭遇（如 `EXOSKELETONS`）只能靠一张手写映射表补全，查不到的会带 `?` 标记。
  现在名称库直接从游戏本地化表取，**遭遇名用游戏原文**
  （`NIBBITS_NORMAL`=「两只小啃兽」、`NIBBITS_WEAK`=「一只落单的小啃兽」，
  比「基础名+（弱）」这种拼接信息量大得多），映射表退化成兜底。
* **名称库不依赖 mod**：早期没装 DanmakuSpire 就只能显示英文 ID。
  现在 `extract` 自己从 `.pck` 提取（含分类，靠 `sts2.dll` 的类型表）。
  顺带修掉两个坑：语言槽位**不能按固定下标取**（中文会在 12 与 13 之间浮动，
  只按位置会取到日文汉字）；中文重名要**按 kind 裁决**
  （真卡 `ASCENDERS_BANE` 曾被告示类杂项 `LEVEL_05` 抢走名字，
  导致 `is_card()` 判错 → 模拟器报假 bug）。详见
  [数据来源.md](数据来源.md) 的「语言槽位」一节。

```
                               用真实对局回放模拟实时（无需启动游戏）
sts2mon stats [--json out.json]  打印全局统计
sts2mon export --format json|csv 导出统计结果

```

## 架构

```
数据源                     适配器                        状态机 / 存储            输出
─────────────────────────────────────────────────────────────────────────────────
.run 存档          ──▶  HistoryAdapter        ──┐
analytics 地图     ──▶  AnalyticsAdapter      ──┤
rdps 战斗明细      ──▶  RdpsAdapter           ──┼──▶ Event 事件流 ──▶ Tracker ──▶ RunState
DamageMeter 状态   ──▶  CombatStateAdapter    ──┘        (EventBus)       (增量重建)     │
（轮询 + diff）                                                                    │
                                                                        Store (SQLite)
                                                                                   │
                                                                     Analytics ────┤
                                                                                   ▼
                                                       Dashboard (http.server + 原生 JS)
```

* **`Tracker` 是唯一的状态机**：实时监控与事后解析共用它，所以两条路径的行为一致、可互相验证。
* **回放即测试**：`demo` 用真实对局生成「DamageMeter 风格」的状态序列并逐回合推进，
  走的是和真机完全相同的适配器 + 事件总线 + 状态机链路。
* **写库是幂等的**：同一场对局可反复导入，不会产生重复数据。
* **多线程安全**：`Store` 为每个线程维护独立连接（sqlite3 连接不可跨线程），写操作统一加锁，
  因此 Web 的多线程 handler 与后台监控线程可以共用一个实例。
* **零第三方依赖**：只用 Python 标准库（http.server + sqlite3 + dataclasses）。

## 自检

```powershell
python tools\selftest.py             # 49 项端到端检查（数据源 -> 导入 -> API -> 回放）
python tools\selftest_live.py        # 30 项真机链路检查（直读游戏写的状态文件）
python tools\selftest_runboundary.py # 17 项「开局即监测 / 换局」检查
python tools\verify_live_nodes.py    # 6 项实时节点/回合/落库检查
python tools\check_sql.py            # 校验 SQL 列数/占位符/实参是否一致
python tools\probe_run.py            # 探查 `.run` 存档结构（调试数据源用）
```

* `selftest.py` 覆盖：数据源发现 → 名称解析 → 数据库导入 → 统计聚合 → 全部 HTTP API →
  真实对局回放 → 实时快照推进 → 事件流落库 → 实时状态持久化。
* `selftest_live.py` 直接读**游戏真实写下的** `DamageMeter_combat_state.json`，验证
  解析 → 首次快照 → 幂等（同一状态 diff 必须为 0 事件）→ 模拟下一回合的增量 →
  轮询 mtime 检测，并断言「逐回合曲线之和 == 累计伤害」（防止重复计数）。

### 两个容易踩的计数陷阱

1. **逐回合曲线只认 `dpt`**：数据源里伤害事件（`events[].t=0`）与 `dpt` 描述的是同一次伤害，
   如果两边都累加就会翻倍。因此伤害事件只进「事件流」，曲线由 `dpt` 按回合写入
   （`Tracker._write_turn_field`，只在值变化时累加增量，反复轮询同一份状态不会重复计数）。
2. **卡牌打出次数有两条路径**：首次读取走绝对值快照（`CARD_STAT`），之后走增量（`CARD_PLAY`）。
   适配器维护一条 `cpc` 基线供两者共用（`CombatStateAdapter._cpc_base`），否则会重复计数。

## 说明

* 程序**只读取**游戏文件；唯一会写入的目录是它自己的 `.sts2mon/`（数据库、日志、回放沙箱）。
  回放用的状态文件写在沙箱里，不会碰到 `DamageMeter_combat_state.json` 本体。
* 实时监控依赖 `DamageMeter` mod（Steam 创意工坊物品 `3747557283`）。
* 游戏版本：`v0.107.1`（Godot 4.5.1 引擎，C# 编写）。
