# 测试说明

测试放在 `tools/` 下，全部**只用标准库**，直接 `python tools\<脚本>.py` 运行。

## 退出码约定

| 码 | 含义 |
|---|---|
| `0` | 全部断言通过 |
| `1` | 有断言失败 |
| `2` | **前置数据缺失**（没跑 `extract`、或没有存档）—— 不是代码问题 |

区分 `1` 和 `2` 是为了让脚本能判定「测试失败」与「环境不具备」。
缺前置数据时脚本会打印数据目录、缺失项、以及该跑哪条命令
（见 `tools/_guard.py`），而不是抛 traceback。

## 分层

不是所有测试在任何环境都能跑 —— 有些需要真实存档或提取数据。
下表是**实测结果**（用 `git clone` 出的干净副本逐条验证过）。

### 第一档：独立可运行（任何环境，无需游戏）

| 脚本 | 覆盖 |
|---|---|
| `selftest_eventscope.py` | 事件归属：每场战斗的事件不能串到相邻楼层 |
| `selftest_live.py` | 真机链路：适配器 → 总线 → 状态机 → 存储 |
| `selftest_runboundary.py` | 对局边界：换局时的重建与残留清理 |
| `selftest_dedup.py` | 重复对局合并（自建临时库） |
| `selftest_floor.py` | 跨 Act 楼层累计（合成数据） |
| `check_sql.py` | SQL 列数/占位符/实参一致性（静态） |
| `simulate_runs.py` | 黑箱模拟器：假造游戏数据跑完整链路 |
| `verify_actor_split.py` | 敌我数据分流 |
| `verify_live_nodes.py` | 实时节点与楼层对齐 |

`simulate_runs.py` 是最有价值的那个 —— 它不需要游戏，却能覆盖
「采集 → diff → 入库 → 分析」全链路，适合当改动前的冒烟测试：

```bat
python tools\simulate_runs.py --runs 25 --seed 1234 --multiplayer-every 5
```

### 第二档：需要先跑 `extract`

| 脚本 | 缺失的文件 |
|---|---|
| `selftest_upgrade.py` | `card_values.json`（升级增量） |
| `selftest_badges.py` | `card_effects.json`（称号分档文案） |

### 第三档：需要真实存档 / 游戏

| 脚本 | 依赖 |
|---|---|
| `selftest_identity.py` | 至少一份**多人** `.run` 存档（本机身份从存档路径推导） |
| `selftest_runend.py` | 任意 `.run` 存档 |
| `selftest.py` | 端到端（多数子项需要存档） |
| `selftest_custommode.py` | `.run` 存档 **+** `card_effects.json`（修正项中文名） |

> `selftest_custommode.py` 对 `card_effects.json` 是**间接**依赖：
> 它通过词典查「选牌」这类修正项名称，源码里不出现文件名，
> 所以静态扫描看不出来，只有跑起来才暴露。分层表按实测归类。

### 需要游戏**正在战斗中**的测试（时序敏感）

| 脚本 | 说明 |
|---|---|
| `selftest_live.py` | 实时链路：读 `DamageMeter_combat_state.json` 走完整状态机 |
| `verify_live_nodes.py` | 实时节点与楼层对齐 |

这两个读的是游戏**实时写出的**战斗状态文件，所以：

* 游戏不在战斗中（`tracking=False`）时，文件里是上一场的残留 → 脚本打印
  说明并以**退出码 2** 结束，不会报假失败。
* 游戏恰好在跑测试的那一两秒里**换场次或结束战斗**，读到的数值会前后不一致，
  可能出现零星断言失败。这不是 bug —— 连续重跑即可确认
  （实测：战斗中连续两次都是全绿）。

不依赖实时数据、随时可跑的替代品：

```bat
python tools\selftest_multiplayer.py    :: 多人局玩家分流（自造状态）
python tools\simulate_runs.py --runs 25 :: 全链路黑箱模拟
```

### 静态检查

| 脚本 | 覆盖 |
|---|---|
| `check_sql.py` | `model.py` 里每条 INSERT 的列数/占位符/实参个数是否一致 |

`check_sql.py` 值得单独说：手写 SQL 最容易犯的错就是这三者数量对不上，
而且往往在运行时才炸。这个脚本用 AST 静态核对，几毫秒出结果。

## 临时目录隔离

不碰真实数据、也不需要游戏的测试，自己建临时 SQLite：

```python
import tempfile
from sts2mon.model import Store
store = Store(Path(tempfile.mkdtemp()) / "t.db")
```

## 界面验收（`tools/ui/`）

用无头 Edge 起 DevTools 协议，对渲染结果做**计算样式断言**，
而不是只看截图。截图容易误判（抓帧早了、缩放差异），所以只作辅助。

| 脚本 | 覆盖 |
|---|---|
| `ui_check.mjs` | 整页/子页切换、主题、滑块、canvas |
| `ui_check_contrast.mjs` | 主题对比度（本机行高亮 vs 涂黑） |
| `ui_check_list.mjs` | 对局列表：无 `?` 行、称号显示 |
| `ui_check_overflow.mjs` | 横向溢出 |
| `ui_check_board.mjs` | 排行榜排序 |
| `ui_check_runs.mjs` | 单人/多人过滤 |

需要先把仪表盘跑起来（`sts2mon.cmd serve`）。浏览器路径会自动探测，
也可用 `CHROME_PATH` 指定；新增脚本请复用 `tools/ui/_common.mjs`
的 `connect()`，不要自己再写一遍浏览器启动与 DevTools 握手。

## 开发调查脚本（`tools/dev/`）

逆向工程期间用的一次性脚本（`probe_*` / `dbg_*`），
用于摸索存档字段、`.pck` 结构、程序集元数据。
它们**依赖真实游戏安装**，不属于回归测试，保留仅供追溯当时的结论。
