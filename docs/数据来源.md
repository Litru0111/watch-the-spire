# 数据从哪来

这一页把「每个字段到底出自哪个文件」写清楚，方便排查「界面上的数字不对」。

所有采集都是**只读**的：程序只读游戏写出的文件，不改写任何游戏数据。

## 目录约定

Windows 上游戏的用户数据目录是：

```
%APPDATA%\SlayTheSpire2\
```

下文用 `<游戏数据>` 指代它。存档按 SteamID 与存档位分目录：

```
<游戏数据>\steam\<SteamID>\modded\profile<N>\saves\
```

> `<SteamID>` 出现在路径里，这是判定「本机玩家」的唯一可靠依据 ——
> `.run` 存档里**没有** local_player_id 字段（实测恒为 None）。

## 各数据源

### 1. `current_run.save`（权威快照）

**位置**：`<游戏数据>\steam\<SteamID>\modded\profile<N>\saves\current_run.save`

提供：当前 HP / 最大 HP / 金币、牌组、遗物、药水、地图路线
（`map_point_history`）、逐层选择（`card_choices` / `upgraded_cards` /
`rest_site_choices`）、对局模式（`game_mode` + `modifiers`）。

**关键限制**：**离开该层才写入**。所以「实时 HP」有一层延迟，
战斗内数据必须靠 DamageMeter 补。

另外这个文件是被频繁**整个重写**的，不是增量追加 ——
所以采集策略是「轮询 + diff」，而不是「跟踪写入位置」。

**楼层怎么算**：`map_point_history` 是各 Act 的点列表，
**包含当前 Act 已结算的部分**（实测：Act3 进行中就有 6 个点）。
总层数 = 各 Act 点数之和。早先误用 `visited_map_coords`（只有当前 Act）
当总数，多 Act 时严重少算，导致回退填充只覆盖前几层、后面的选择全丢。

### 2. `DamageMeter_combat_state.json`（战斗内）

**位置**：`<游戏数据>\DamageMeter_combat_state.json`

提供：当前遭遇、回合数、敌我 HP、逐回合伤害、逐卡伤害与增益。

由游戏内 mod **DamageMeter** 写出。`tracking` 为 false 表示这份数据是
**上一场战斗的残留** —— 必须丢弃，否则旧战斗会被算进新战斗。

### 3. `skada_run_token.json`（新对局的第一信号）

**位置**：同上目录

提供：`StartTime` / `CharacterId` / `Ascension` / `PlayerCount`。

它比战斗状态文件**更早**出现（开局就有），所以用来判断「这是新的一局」。
`StartTime` 与 `current_run.save` 推导出的对局标识是同一个值，两个源因此能对齐。

### 4. `rdps_meter\<seed>.json`（逐卡明细）

**位置**：`<游戏数据>\rdps_meter\`

提供：更细的逐卡伤害/增益/Debuff，以及玩家名单（含 NetId）。

### 5. `history\*.run`（对局结束后的完整存档）

**位置**：`<游戏数据>\steam\<SteamID>\modded\profile<N>\saves\history\`

文件名是对局的 `start_time`。这是**最完整、最权威**的来源，
也是「历史对局」列表的数据基础。里面的 `players[].badges` 是**对局结束获得的称号**。

> 单人局的 `players[0].id` 是**整数 1**，不是 Steam ID。

### 6. `object-catalog.json`（中文名称库）

**位置**：`<游戏数据>\DanmakuSpire\object-catalog.json`

提供：卡牌/遗物/怪物/事件的 ID → 名称。由 DanmakuSpire mod 导出。

**它不含药水与自定义修正项** —— 这两类的名称得从 `.pck` 文案表里取。

### 7. `logs\godot.log`（出牌日志）

**位置**：`<游戏数据>\logs\godot.log`

提供：`dealt <卡名> <数值>` / `from <卡名> <数值>` 形式的伤害归因，
用于把伤害精确算到每张牌上。

## 提取数据（`sts2mon extract`）

公开仓库**不包含**这些文件：它们是游戏的本地化文案与编译常量，
属于游戏版权内容。用一条命令在你自己的机器上重建：

```
sts2mon.cmd extract
```

| 产物 | 来源 | 方法 |
|---|---|---|
| `card_effects.json` | `SlayTheSpire2.pck` + 各 mod pck | 扫本地化表（14 种语言按固定顺序，中文恒为下标 13） |
| `card_values.json` | `sts2.dll` | 纯 Python 解析 .NET 元数据表 + 反汇编 IL 取 `CanonicalVars` / `OnUpgrade` |
| `power_names.json` | 上一步的文案 | 从 `{XxxPower}层[gold]中文[/gold]` 形态里挖出对照 |

### 耗时

实测（本机，游戏本体约 1.8 GB）：

| 步骤 | 耗时 | 说明 |
|---|---|---|
| `extract_effects.py` | ~3 秒 | 扫 1813 MB 的 pck，按字节找本地化键 |
| `extract_values.py` | ~5 秒 | 只处理 8.9 MB 的 dll，但要反汇编 IL |
| `build_power_names.py` | ~0.2 秒 | 纯文本处理 |
| **合计** | **~8 秒** | |

> 早先这一步要 **5 分钟**。原因不是数据量大，而是 `dotnet_meta` 缺缓存：
> `read_row` 每次调用都重新解析列规格字符串（一次提取需调用 337 万次），
> `typedefs()` 每次都在重建 9410 个类型表（被调用数十次，累计 43 秒）。
> 两处缓存后提速约 40 倍，且提取结果逐字节一致。

### 为什么语言判定要按「顺序」而不是「看内容」

`.pck` 里同一条文案会以 14 种语言重复出现，且**没有语言标记**。
只知道它们按固定顺序排列（德、英、西、法、意、日、韩、波兰、葡、俄、西、泰、土耳其、**中**），
所以中文恒为下标 13。早先靠「含汉字」猜语言，把日文 `複製薬` 误判成中文，
同时漏掉真正的中文 `复制药水`。

### 升级增量是怎么拿到的

卡牌升级**不换 ID**，只是数值变化，而数值编译在程序集里。
`OnUpgrade` 的 IL 形态很规整：

```
callvirt  DynamicVarSet::get_Damage     # 哪个变量
ldc.i4.3 ; newobj Decimal::.ctor        # 增量 +3
callvirt  DynamicVar::UpgradeValueBy    # 应用
```

于是不必执行代码，扫一遍指令就能取出「变量 → 增量」。
两种写法都要处理：具名属性，以及索引器形态
（`ldstr "AccuracyPower"; callvirt get_Item`）。

## 判定不了的

- **是否用过 SL（读档）** —— 游戏不留下任何痕迹，无法检测。
- 实时数据的「本机是谁」，在没有存档路径（纯实时启动）时只能先假定第一位。
